# RFC: вопросы типа «код» и advisory-отчёт похожести

**Статус:** proposal. Этот RFC не реализуется в текущем этапе.

## Цель

Добавить вопрос типа `code` так, чтобы исходный код ученика не исполнялся в базе данных, браузере преподавателя или Edge Function, а результаты похожести помогали преподавателю начать проверку, но не служили доказательством списывания.

## Предлагаемая модель

1. В опубликованной версии хранить язык, ограничения ресурсов, закрытый набор тестов и публичное описание задачи. Закрытые тесты и эталонные решения остаются в `private`-схеме.
2. При сохранении хранить текст решения как ответ попытки; он не попадает в клиентский bundle, CSV или общий аудит.
3. Оценивание запускать только в изолированном одноразовом runner: без сети, с read-only образом, непривилегированным пользователем, лимитами CPU/RAM/времени/размера вывода и отдельной очередью. Runner получает минимальный короткоживущий capability-token, а не service-role ключ.
4. Runner возвращает структурированный результат: статус запуска, результаты тестов, лимиты и краткий безопасный stderr. Полный инфраструктурный лог и закрытые тесты не показываются ученику.
5. Идемпотентность привязать к хешу неизменяемого ответа и версии тестов. Повторный запуск не создаёт второй академический результат без явной команды преподавателя.

## Похожесть решений

Пайплайн должен сначала нормализовать код по языку, затем сравнивать токены/AST и учитывать общие шаблоны задания. Отчёт видит только преподаватель-владелец и содержит: пары попыток в его области, метод, версию алгоритма, уровень уверенности, исключённые шаблоны и ссылку на ручную проверку.

Это **advisory-сигнал**, не доказательство. Он не меняет балл, статус попытки, доступ ученика и не создаёт санкций. Пороговые решения, контакт с учеником и любые последствия остаются ручным действием преподавателя с контекстом задания.

## Перед реализацией

- провести security review runner-инфраструктуры и supply-chain образов;
- определить допустимые языки, квоты, retention исходного кода и процесс удаления;
- провести DPIA/проверку локальных требований к данным учащихся;
- добавить adversarial tests: бесконечные циклы, fork bomb, сетевые запросы, большие выводы, вредные архивы и обход sandbox;
- согласовать UX ручной проверки и процедуру оспаривания результата похожести.
