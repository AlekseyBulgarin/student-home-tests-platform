# Архитектура

## 1. Контекст и цели

Первая версия поддерживает сквозной сценарий:

1. преподаватель импортирует JSON и редактирует черновик;
2. публикует неизменяемую версию теста;
3. назначает версию конкретному ученику и получает секретную ссылку;
4. ученик без регистрации начинает или восстанавливает попытку;
5. ответы сохраняются и проверяются на сервере;
6. ученик и преподаватель получают отчёты в пределах своих прав.

Система не пытается доказать списывание. Журнал браузерных событий — неполная недоверенная телеметрия, которая показывается отдельно от учебной оценки.

## 2. Компоненты

### Web-клиент

Один React SPA с двумя маршрутными областями:

- `/teacher/*` — кабинет преподавателя, защищённый Supabase Auth;
- `/a/:token` — ученический сценарий по секретной ссылке.

Клиент отвечает за отображение, локальное состояние формы, очередь автосохранения и сбор разрешённых событий. Он не получает сервисный ключ, закрытые ключи вопросов, итоговую оценку до отправки или серверные идентификаторы вне необходимой области.

### Supabase Auth

Используется только для преподавателей. Профиль преподавателя связывается с `auth.users.id`. Создание преподавателей в первой версии выполняется через приглашение/панель Supabase; публичная регистрация отключена.

### PostgreSQL

Хранит доменные данные. RLS включена на всех таблицах публичной схемы. Преподавательские запросы ограничены `teacher_id = auth.uid()`. Ученический клиент не читает таблицы напрямую.

### Edge Functions

Доверенная граница для всех операций ученика и чувствительных операций преподавателя:

- импорт и серверная валидация теста;
- публикация версии;
- создание/отзыв назначения и выдача секрета один раз;
- проверка токена, начало/восстановление попытки;
- получение безопасной проекции вопросов;
- автосохранение ответов;
- приём событий;
- идемпотентная отправка и серверное оценивание;
- формирование отчётов;
- удаление данных ученика.

Edge Functions используют service role только внутри серверной среды. Функции сначала устанавливают область доступа, затем выполняют минимальную транзакцию или RPC с фиксированным `search_path`.

## 3. Границы доверия

Недоверенными считаются:

- все параметры клиента, включая `student_id`, `assignment_id`, `attempt_id`, баллы, время и sequence;
- имя ученика;
- импортируемый JSON;
- клиентский таймер и журнал событий;
- localStorage, URL, заголовки браузера и состояние fullscreen.

Доверенными после серверной проверки считаются:

- `auth.uid()` преподавателя;
- запись назначения, найденная по хешу валидного токена;
- серверное время PostgreSQL;
- опубликованная версия и закрытые ключи из БД;
- результаты, рассчитанные серверной функцией в транзакции.

## 4. Потоки данных

### Импорт и публикация

JSON проходит проверку размера до разбора, затем Zod-валидацию, доменные проверки уникальности и ссылочной целостности. Ошибки возвращаются как `{ path, code, message }`. Черновик хранится отдельно от опубликованной версии. Публикация атомарно создаёт снимок версии, вопросы, варианты, ключи и темы. После публикации UPDATE/DELETE защищены триггером и правами.

### Назначение и секретная ссылка

Сервер генерирует 256-битный случайный токен. В БД сохраняются только `SHA-256(token)` и короткий безопасный префикс для поддержки. Полный токен возвращается один раз и помещается во fragment ссылки (`/a#token=...`) либо немедленно удаляется из адресной строки после загрузки. Предпочтителен fragment: он не отправляется серверу как Referer. Страница попытки задаёт `Referrer-Policy: no-referrer`.

### Активная попытка

`resolve-assignment` принимает токен, нормализует его, хеширует и проверяет срок/отзыв/лимит. Клиент получает непрозрачную короткоживущую attempt-сессию, привязанную сервером к одному назначению и попытке. Все дальнейшие операции требуют эту сессию; переданный клиентом `attempt_id` не является доказательством доступа.

Безопасная проекция вопроса содержит только `id`, `type`, `text`, варианты, баллы и темы. Поля `correct_option_ids`, общее объяснение и объяснения вариантов исключены на уровне SQL/RPC и DTO.

### Автосохранение

Клиент присваивает каждой команде монотонный `client_revision`. Сервер блокирует попытку, проверяет дедлайн и состояние, затем принимает только ревизию больше сохранённой. Ответ возвращает принятую ревизию и серверное время. Это устраняет перезапись свежего ответа устаревшим запросом из другой вкладки.

### Отправка и оценивание

Команда содержит `idempotency_key`. Транзакция блокирует попытку, повторно проверяет дедлайн, состояние и версию, нормализует ответы, вычисляет баллы по закрытым ключам и сохраняет неизменяемый снимок результата. Повтор с тем же ключом возвращает прежний результат. Повтор после `submitted` не пересчитывает результат.

## 5. Оценивание

- `single_choice`: полный балл только за единственный правильный вариант;
- `multiple_choice`: полный балл только при точном равенстве множеств выбранных и правильных вариантов; порядок не влияет;
- иные типы отклоняются при импорте первой версии.

Тематический процент: сумма полученных баллов по вопросам темы / сумма максимальных баллов этих вопросов. Вопрос с несколькими темами целиком учитывается в каждой теме; поэтому суммы по темам не обязаны совпадать с итогом теста.

## 6. Нефункциональные решения

- HTML из импорта не рендерится; весь контент выводится как текст.
- CSP и `Referrer-Policy: no-referrer`; сторонние трекеры на ученических страницах отсутствуют.
- Ограничение частоты для проверки токена и старта попытки: серверная таблица скользящих окон по хешу токена и хешированному сетевому признаку, с коротким TTL; конкретные лимиты конфигурируются.
- Секреты не попадают в URL query, логи, аналитику, исключения и client storage.
- Retention настраивается; фоновая очистка может запускаться Supabase Cron, если он доступен на выбранном тарифе, либо документированной внешней cron-командой.
